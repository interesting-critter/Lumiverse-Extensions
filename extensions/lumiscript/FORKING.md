# Forking LumiScript

**LumiScript is MIT-licensed. You're welcome to fork it. This is the minimum factual starting point.**

## Status

- **Forks are unofficial and unsupported.** The upstream maintainer doesn't review external PRs, doesn't merge fork changes, and doesn't run a formal support process. Bug reports against fork-specific code aren't acted on.
- **That said, the door isn't shut.** If you're putting honest work into a fork and want to discuss architecture, propose an RFC, or ask a design question that needs the upstream author's context, you can reach `mindbound` on Discord. No commitment to act on anything — but the conversation channel exists, and substantive questions get answered when time allows.
- **The MIT license is in [`LICENSE`](LICENSE).** Those are the actual terms governing your use of this code — not anything written in this document.
- **No roadmap commitments.** Upstream behaviour may change without warning between releases in ways that affect forks. Versioning is `1.0.0-rc.X` heading toward GA; expect surface churn until then.

## Build

LumiScript is a Bun project. Node and npm are not supported as toolchains.

```bash
bun install                    # install dependencies
bun run build                  # full build chain: corpus gen + three typechecks + three bundles
bun test                       # run the test suite
```

The full `bun run build` chain produces three `dist/` outputs:

- `dist/backend.js` — bundled from `src/backend.ts`, target `bun`, minified.
- `dist/script-runner.js` — bundled from `src/script-runner/child-entry.ts`, target `bun`, minified.
- `dist/frontend.js` — bundled from `src/frontend.tsx`, target `browser`, minified.

Individual targets, typechecks, and corpus generation are available as separate scripts in `package.json#scripts` — `bun run build:backend`, `bun run typecheck`, `bun run gen:corpus`, etc. See `package.json` for the full list.

## Architecture in one paragraph

LumiScript is a Spindle extension with two server-side processes and one browser-side surface. The **backend worker** (`src/backend.ts` → `dist/backend.js`) runs in Lumiverse's Bun-worker extension host and handles script storage, event routing, persistence, and dispatching user-script execution requests. The **script-runner subprocess** (`src/script-runner/child-entry.ts` → `dist/script-runner.js`) is a separate Bun subprocess spawned via Spindle's backend-process API; user-script bodies execute here inside hardened `new AsyncFunction` sandboxes (see `src/script-runner/child-entry.ts:installSandboxLockdown` for the runtime allowlist). The two communicate via typed IPC envelopes defined in `src/types/script-runner-ipc.ts`. The **frontend** (`src/frontend.tsx` → `dist/frontend.js`) runs in the browser and renders the script editor, reference tab, and per-script UI surfaces. Backend ↔ frontend messaging goes through Spindle's `sendToFrontend` / `onFrontendMessage` channels.

## What's not in the public tree

- **`notes/`** — gitignored. Dev scratch, design journals, post-mortems, scoping docs. Contains assumptions and historical context that don't survive being removed from the surrounding conversation; not useful to a fork.
- **`CLAUDE.md`** — gitignored. Personal Claude Code working context, accumulated over the development arc. Mostly memory cues for the upstream author rather than reusable documentation.
- **Personal LLM memory files** (outside the repo) — used by the upstream author during development to track project state, decisions, and known issues. Not portable.

If you fork, you'll have to rebuild internal context as you go. Three things in the repo that help:

1. The `src/` tree is JSDoc-rich — engine modules, API builders, and shared utilities have block comments describing intent and edge cases.
2. The in-app Reference tab (rendered from `src/components/reference/ReferenceTab.tsx`) is the most up-to-date overview of the user-facing API surface. The tab has a Markdown export.
3. `docs/` contains the public prose docs for script authors — useful background for understanding what the extension is supposed to do from a user's perspective.

## Running a fork against Lumiverse

Lumiverse loads installed extensions from `data/extensions/<identifier>/repo/`, where `identifier` comes from `spindle.json#identifier`. To run a fork:

1. **Change the identifier.** Don't ship a fork with `identifier: "lumiscript"` — it will collide with the upstream extension on any Lumiverse install that has both. Update `identifier`, `name`, `author`, `github`, and `homepage` in `spindle.json` to reflect the fork.
2. **Build:** `bun run build`.
3. **Install:** either point Lumiverse's "install from URL" flow at your fork's GitHub repo, or place the built tree directly at `data/extensions/` and toggle the extension on in Lumiverse's Extensions panel.

`minimum_lumiverse_version` in `spindle.json` is the floor for the host version that supports the manifest features the extension uses. LumiScript currently sets it to `1.0.4` (the latest stable Lumiverse at the v2.0 release). Bump it if your fork relies on newer manifest features, or lower it if you've verified an older host works for your fork.

Lumiverse must be restarted (or the extension toggled off/on) to pick up new builds.

## Lumiverse's license is separate

LumiScript is MIT-licensed (above). The **Lumiverse platform** that LumiScript runs on as a Spindle extension is licensed *separately* — under the **Lumiverse Community License v2.0** (LCL), shipped as `LICENSE.md` in the [Lumiverse repository](https://github.com/prolix-oc/Lumiverse). The LCL is a custom source-available license; per its own §5.5, it is **not OSI-approved and is not directly compatible with MIT, GPL, Apache, or BSD**.

What this means for a LumiScript fork:

- **Your fork's source remains under MIT** (or whatever license you apply to your changes — see your own license file). Forking MIT-licensed LumiScript doesn't subject your fork's source to the LCL. The two licenses cover different code.
- **Your *use* of Lumiverse to run your fork is governed by the LCL.** Most relevant LCL clauses for a forker: no public-facing deployment of Lumiverse, no commercial use without a separate commercial license, no use of Lumiverse materials as AI/ML training data, contribute-back obligations on improvements to Lumiverse itself, no use by government entities. Read the LCL directly — it's the authoritative source on what you can and can't do with Lumiverse, and a brief summary in this doc can't substitute.
- **Extensions integrate with Lumiverse via the public Spindle API.** The typed surface is the `lumiverse-spindle-types` package (an npm dep of LumiScript). The Spindle API is the integration boundary — extensions sit alongside Lumiverse rather than inside it, which is what lets a LumiScript fork keep its MIT license despite Lumiverse's LCL covering the platform itself.

This section is orientation, not legal interpretation. If your use is anywhere near the LCL's edges (commercial work, public deployment, modifications to Lumiverse's tree rather than just LumiScript's), read the full LCL and consult counsel if appropriate.
